# FusionMob

**FusionMob** is an **Autodesk Fusion 360 add-in** for parametric furniture (cabinet) design that also exports a cut list ready for import into **CorteCloud** (a Brazilian panel-cutting / nesting service). It targets Brazilian *marcenaria* (custom cabinetmaking) workflows.

## What it does

Inside Fusion 360, it adds a **FusionMob** ribbon tab (in the Solid environment) with a **Cabinet** panel containing five commands:

| Command | Purpose |
|---|---|
| **New Panel** | Create a single parametric panel (board) with dimensions, material, function, and edge-banding (*fita*) per edge. |
| **Edit Panel** | Select one or more tagged bodies and change their edge-banding (*fita*) per edge (Nenhuma / 0.4mm / 1mm), rewriting the `panelData` attribute in place — no geometry rebuild. Also on the right-click menu when a tagged body is selected. |
| **New Cabinet** | Generate a full frameless cabinet carcass: two sides, base, top, N evenly-spaced shelves, an optional grooved back panel, an optional toe kick (*rodapé*), optional doors (*portas*), and optional drawers (*gavetas*) with embedded slide hardware. |
| **Edit Cabinet** | Pick an existing cabinet, tweak any parameter, and regenerate it in place. Defers to **Cabinet Layout** for cabinets that carry a multi-region layout (which the flat dialog cannot represent). |
| **Cabinet Layout** | Open a visual HTML **palette** to divide the cabinet interior into a recursive grid of *regions* — each independently open / shelves / doors / drawers — split them horizontally/vertically, resize or merge them, then **Apply** to (re)generate the whole cabinet. This is the "try different configurations without touching individual bodies" editor. |
| **Export Cut List** | Collect every tagged panel in the document and write a CorteCloud-compatible CSV. |
| **Preferences** | Open an HTML **palette** to edit the persistent **material library** (add/edit/remove *chapas*) and the **default cabinet parameters** (dimensions, fita, hinge/drawer/hardware, toe kick, …). Saved to a per-user JSON file so every new cabinet opens pre-filled; per-cabinet overrides are unaffected. Keeps **several named profiles** (variations — shop standard / client / job) with one active, and **exports/imports** them as `.json` files to move a setup between machines. |

## Architecture

Two conceptual layers:

- **Layer 1 (geometry):** Builds 3D solid bodies (one component per panel) and stores each panel's cut-list definition as JSON in a Fusion **body attribute** (group `FusionMob`, name `panelData`). Cabinets also store their full creation config as JSON on the cabinet component (`cabinetConfig`), enabling non-destructive edit/rebuild.
- **Layer 2 (export):** Reads those stored JSON attributes back out (`findAttributes`) and writes the CorteCloud CSV.

Geometry is created with `TemporaryBRepManager` boxes (with boolean-difference cuts for dado grooves and toe-kick notches) so parts land at exact coordinates. Panels are locked together via as-built rigid joints, falling back to a rigid group. Drawer **slide hardware** is the one exception to the build-from-scratch rule: it is either a lightweight parametric proxy box or a real CAD model imported from the bundled hardware library (see *Drawers* below).

### Key domain details
- **Interior layout (region grid):** the cabinet interior is a **recursive region tree** stored as `cfg['layout']`. A node is either a **split** (`{'split':'v'|'h','children':[{size,fixed,node},…]}`) or a **leaf** (`{'type':'open'|'shelves'|'doors'|'drawers'|'blind', count, inset, …}`). A `'v'` split stacks rows top-to-bottom (horizontal dividers between them); an `'h'` split places columns left-to-right (vertical dividers). Child `size` is either absolute mm (`fixed:True`) or a flex weight sharing the leftover space; a divider panel of carcass thickness sits between consecutive children. `build_cabinet` walks this tree with a **pure planner** (`plan_layout` → leaf *bands* + divider specs; `split_child_extents` is the single source of truth for child positions, shared with validation so they can't drift) and dispatches each leaf to a band-aware builder (`build_shelves`/`build_doors`/`build_drawers`/`build_blind`/`build_open`) that renders inside an arbitrary `[x0,x1]×[z0,z1]` band. A **`blind`** leaf is a fixed *painel cego* — a single solid front (overlay default / inset), grain-locked and edge-banded like a door but with no hinge/joint, joined to the rigid carcass to simply block access to that region (e.g. the dead corner of an L-shaped run); it is a layout-palette-only type (function `Cego`) and is not reachable from the flat New/Edit dialog. A *band* carries per-side overlay reach (`ext_*`, how far a *sobreposta* door/face covers the bounding panel) and the key of the vertical panel bounding it in X, so hinge mounting-plate holes bore into the right body (a carcass side **or** a vertical divider). **`normalize_cfg` is backward compatible:** a legacy config with no `layout` (or the classic New/Edit dialog, which never sets one) synthesizes a single top-level leaf from the flat fields (`_synthesize_layout_from_flat`), so a single-region cabinet reproduces the classic full-carcass geometry exactly. The **Cabinet Layout palette** writes an explicit tree; when one is present it is authoritative for the build. Interior dividers are tagged `panelData` (functions `Lateral` for vertical, `Prateleira` for horizontal) so they reach the cut list; v1 limitation — interior dividers carry no back grooves and stop at the back panel's front face. Because a leaf's type is per-region, **shelves, doors and drawers now coexist in one cabinet** (in different regions); the old shelves-vs-drawers and overlay-doors-vs-overlay-drawers mutual-exclusion rules are gone — the `ext=t/2` overlay rule makes adjacent overlay fronts meet at the divider centreline without overlapping.
- **Units:** UI/CSV use millimeters; Fusion's internal geometry uses centimeters (the code converts by ÷/×10).
- **Dimensions are FINISHED sizes** — CorteCloud deducts edge-tape thickness itself, so the add-in does not pre-deduct. Thickness is encoded in the material name (e.g. `MDF 18mm Branco`).
- **Edge banding (fita):** the CSV's four `Fita C1/C2/L1/L2` columns are auto-populated on build for the **visible** edges only. C1/C2 tape the two Comprimento (longer) edges, L1/L2 the two Largura (shorter) edges. `make_panel_data` takes either `band=` (a tape name → all four edges, used for doors/drawer faces) or `bands={'a':(t,t),'b':(t,t)}` — per-edge banding expressed relative to the two dims the caller passes (`'a'` = the pair of edges of length `dim_a`), mapped to C/L by the same larger→Comprimento rule so a single front edge (`bands={'a':(tape,'')}`) always lands in the right column. The builder auto-bands the **front** edge of sides/base/top/shelves/dividers and the **top** edge of the toe-kick front board; doors/faces stay banded all round; the back panel, drawer-box interior, and rear/end edges stay blank. Tape choice lives in the module-level `FITA` dict + per-cabinet `cfg['fita']` (deep-merged in `normalize_cfg`, resolved by the pure `fita_tape`): two editable tape names (`name_thin` 0.4mm / `name_thick` 1mm) and a thickness per part group (`carcass` default `thin`, `fronts` default `thick`, each `none|thin|thick`). Exposed as a top-level **Fita (fita de borda)** group in the New/Edit Cabinet dialog, as its own **Fita de borda** section in the Cabinet Layout palette, and as a step in the palette's setup **wizard** (the old per-command *Fita da porta/frente* fields are gone — fronts now source their tape here). Since fita is pure cut-list metadata (never modelled), the **Edit Panel** command (ribbon + right-click on a tagged body) overrides the four edges on any individual body by rewriting its `panelData` attribute in place — no rebuild. Legacy `door_band`/`drawer.face_band` keys are accepted-but-ignored so older stored configs still load.
- **User preferences (cross-document/session):** Fusion has no application-level settings store for add-ins (only per-document entity attributes), so preferences live in a JSON file at a **writable per-user location** — `%APPDATA%\FusionMob\preferences.json` on Windows, `~/Library/Application Support/FusionMob/preferences.json` on Mac (**never** under `RES_DIR`, the install folder, which is read-only and wiped on update). Loaded lazily + cached and degrading to an empty store on any error, exactly like `load_hardware_manifest`. Shape (**v2**): `{version:2, active_profile, profiles:[{name, materials:[{name,thickness}], cabinet_defaults:{…partial cfg…}}]}`. Two accessors are the single seams the rest of the add-in reads through: **`get_materials()`** (the active profile's material library, else the built-in `MATERIALS` seed — thickness is informational, part geometry uses per-part `t`) and **`effective_default_cfg()`** (`normalize_cfg` of `DEFAULT_CFG` deep-merged with the active profile's `cabinet_defaults`, so absent/new keys backfill from factory). New Panel/New Cabinet dialogs, the Cabinet Layout palette (`_palette_state`/`_palette_target`), and the Preferences palette all source their material lists and starting cfg through these, so per-cabinet edits (saved only to that cabinet's `cabinetConfig`) still override freely. Stored `cabinet_defaults` never pins an interior `layout` (stripped on save) so New Cabinet keeps synthesizing a single region.
  - **Profiles (variações) + export/import:** a **profile** is one complete named variation of the configuration — material library *and* cabinet defaults switched together (shop standard vs. a client vs. a job). `profile_names()` / `active_profile()` sit under the two accessors, so switching the active profile changes what every dialog opens with and nothing else. The pure **`migrate_prefs(data, default_name)`** normalizes *any* preferences document into the v2 store and is the single reader for both the on-disk file and imported ones — a **v1 file** (`{version:1, materials, cabinet_defaults}`, no profiles) becomes a single `Padrão` profile on load, so upgrading loses nothing (the v2 shape is written back on the next save). The Preferences palette's profile bar drives `PrefsPaletteHTMLHandler` actions `profileSelect`/`profileCreate` (blank or `copy_current` duplicate) / `profileRename` / `profileDelete`, plus `export` and `import`. **Export** (`_prefs_export`, `scope:'active'|'all'`) writes a `{kind:'fusionmob-preferences', version, app_version, active_profile, profiles}` JSON through a Fusion file dialog — it exports *what the editor shows* without saving to the store; **import** (`_prefs_import`) reads such a file (or a legacy `preferences.json`, named after the file stem), **adds** its profiles renaming collisions via `_unique_name` (never overwrites a saved profile) and activates the first. Every profile/export action carries the editor's pending edits, which `_stage_edits` folds into the *current* profile first so switching can't lose work; edits that fail `validate_cfg`/`_clean_materials` are dropped with a `note` instead of blocking the switch. All mutations go through `_store_copy()` so a failed or cancelled operation can't desync the cache from the file. `reset` restores factory values **in the active profile only** (other profiles untouched); `clear_preferences` (deleting the whole file) is now only the no-profile fallback. Deleting the last remaining profile is refused — reset it instead. Palette-side, name entry and delete confirmation use inline `.ask` rows, since a Fusion palette can't rely on `window.prompt`/`confirm`. Because those defaults now live in Preferences, the **New/Edit Cabinet dialog opens minimal** — only Largura/Altura/Profundidade, Prateleiras and Material show; a **`Configuracao avancada`** checkbox (`advancedMode`) reveals the rest (thickness, shelf-align, Fundo, Rodape, Portas, Gavetas, Fita, and the tol/hinge Advanced group). Visibility is toggled by `_apply_cabinet_advanced_visibility` over `_CABINET_ADVANCED_IDS` from the New/Edit `inputChanged` handlers; it is purely cosmetic — `read_cabinet_inputs` reads every input by id regardless of visibility, so hidden defaults still drive the build. The **Cabinet Layout palette** (`layout_editor.html`) has the same gate: a `Configuracao avancada` switch (`#advancedMode`, `applyAdvanced`) hides the `secStructure`/`secFronts`/`secFita`/`secAdvanced` sections by default, leaving only the medidas + interior region editor; `readCfgFromForm` still reads the hidden fields.
- **Editing model (delete-and-rebuild, not native-parametric):** every panel is a static BRep body committed into a Fusion `baseFeatures.add()` — there are **no** sketches/extrudes/driving dimensions, so Fusion User Parameters cannot drive the geometry. Editing therefore captures the cabinet's position, deletes the whole occurrence, and re-runs `build_cabinet` from the (edited) `cabinetConfig` (Edit Cabinet and the Cabinet Layout palette's Apply share this flow). Three things make that rebuild feel parametric and non-lossy: (1) **`publish_user_parameters`** mirrors the key dimensions to **informational** Fusion User Parameters named `fmob_<param_prefix>_<field>` (mm via `ValueInput.createByString`, never `createByReal`), so the model *reads* as parametric in the Parameters table — editing them there does nothing (static geometry), as the stamped comment says; `param_prefix` is a stable per-cabinet slug (`_next_param_prefix` picks the lowest unused `c<N>`) carried in cfg so rebuilds update the same params instead of colliding across cabinets, and it survives edits via `_carry_forward_cabinet_cfg`. (2) **Per-panel fita overrides survive rebuild:** Edit Panel now also writes each body's four `fita_*` into the owning cabinet's `cfg['panel_overrides']` (keyed by the body's stable slot name, e.g. `Base`/`Prateleira 1`/`Gaveta 2 Frente`), and `build_cabinet` re-applies them as each tagged body is created (module-level `_ACTIVE_PANEL_OVERRIDES` read inside `add_solid_panel`/`add_solid_body` via `_apply_panel_override`). Both `panel_overrides` and `param_prefix` are backfilled by `DEFAULT_CFG`/`normalize_cfg` and carried across edits (the flat dialog / palette don't round-trip them). (3) **User-applied appearances survive rebuild:** `capture_cabinet_state` snapshots non-null `body.appearance` overrides by slot name before delete and `restore_cabinet_state` re-applies them onto the rebuilt occurrence; slots that vanish on a topology change are skipped. The whole build is wrapped in a named **timeline group** (`FusionMob <name>`, parametric designs only) so it reads as one unit; Edit Cabinet is already one undo step (a Command execute), while the palette Apply — an `HTMLEventHandler` — is not, so it lands as several undo entries (accepted). Orphaned `fmob_*` params from a manually deleted cabinet are left behind (documented limitation).
- **Back panel** mounting is configurable per cabinet via `cfg['back_mode']` (default `'groove'`; backfilled by `DEFAULT_CFG`/`normalize_cfg` so older stored configs load). **`groove`** (*encaixado*, classic): seats in dado grooves cut into the sides/base/top, with configurable clearances; the interior datum `back_front_y = D − back_setback − back_t`. **`overlay`** (*sobreposto*): a full-width × full-carcass-height board applied (screwed) to the rear — its front face flush with the sides/base/top rear edges (`y = D`) and extending `back_t` behind, so it never shares volume with the carcass (no grooves, no interference) and the interior runs full depth (`back_front_y = D`). In overlay mode `back_setback`/`dado_depth` and the dado clearance checks are inert (validation skips them); the New/Edit dialog shows a **Fixação do fundo** dropdown, and both palettes hide the recuo/ranhura fields and swap the back schematic (`back` ↔ `back_overlay`) to match the selected mode.
- **Toe kick** is a separate box the carcass rests on (standard BR practice), with the cabinet's overall height *including* the base.
- **Side↔base/top joinery (Fixação Lateral):** how the side panels (*laterais*) meet the base and top is configurable per junction via `cfg['joinery']` (module-level `JOINERY` defaults, deep-merged in `normalize_cfg` like `hinge`/`tol`/`fita`). Two keys per junction — `bottom_mode`/`top_mode` (`'aligned'` | `'over'`) and `bottom_overhang`/`top_overhang` (mm). **`aligned`** (both default) reproduces the classic geometry exactly: base/top captured **between** full-height sides. **`over`** runs the base/top the **full width** (`W`) with the side sitting on/under it, so the side's Z-extent shrinks. The design invariant that keeps this contained: the **interior datums never move** — `root_band.z0 = z_off+tc` (base top face) and `z1 = z_off+Hbox_c-tc` (top bottom face) are unchanged — so the region grid, back panel, shelves, doors, drawers and hinge boring are all unaffected; only the side box Z-extent + cut-list length and the base/top X-extent + cut-list width change. `overhang` (mm) is how far the side reaches past the panel's inner face toward its outer face (0 = rests on/under the panel; `=t` = flush with its outer face; `>t` = skirts beyond, clamped to the floor at the bottom with a build `warnings` note). A separate **`sides_to_floor`** flag (checkbox *Laterais até o piso (pés laterais)*) controls the toe-kick↔side relationship: when off (default) the sides stop at the base bottom (`z_off`) and the toe kick is a separate **full-width box** below (today's behaviour); when on (and there is a toe kick) the side panels run down to the floor (`side_z0 = 0`) as the cabinet **legs**, and the toe-kick front board + back rail + reinforcements span **between** the sides (recessed) with no end legs. The base top face stays at `z_off+tc` either way, so the interior is unaffected; the side just gets longer and the kick boards drop to `inner_w`. Because a full-width panel and a skirting side would share volume, the builder cuts a matching **end-rebate** (*rebaixo*) into the panel with the same `TemporaryBRepManager` boolean path as the dado grooves so parts stay flush with no interference; since CorteCloud has no *usinagem* field, the rebate depth is appended to the panel's `Complemento` (same convention as hinge/slide *furação*). Exposed as a gated **Fixação lateral** group in the New/Edit dialog, a **Fixação lateral** section in the Cabinet Layout palette with an **editable SVG diagram** (front-elevation schematic; the two overhangs are number inputs overlaid on the drawing, live-redrawn on change), and a section in Preferences. **v1 scope: vertical joinery only** — Promob's depth-direction *Folga/Alinhamento* (F/G/H/I) is not modelled.
- **Tamponamento (acabamento):** optional applied finishing panels over the **exposed faces** of the carcass — left side, right side, and/or top — configured per cabinet via `cfg['tamponamento']` (module-level `TAMPONAMENTO` defaults, deep-merged in `normalize_cfg` like `joinery`/`hinge`/`tol`/`fita`). Six keys: three independent face toggles (`left`/`right`/`top`), a thickness `t` (mm), a `material` (blank `''` inherits the carcass material), and a `front_overhang` (mm). Geometrically modelled like the **overlay back panel** — each enabled face becomes a single applied `add_panel(...)` placed **outside** the structural face, so it **adds to the overall envelope** (width grows by `t` per side panel, height by `t` for the top). Side panels run the **full height** (`Z ∈ [0, Hc]`, floor-to-top, covering the toe-kick recess); the top panel caps the **full finished width** (spanning the side tamponamentos when present). **Depth:** the panels' rear edge stays flush with the cabinet back (`y = Dc`) and they project **forward** past the carcass front by `front_overhang` (front edge at `y = −front_overhang`), so their depth is `D + front_overhang` (`0` = flush) — applied uniformly to sides + top so the finished shell lines up at the front. Because they sit outside the box, the **interior datums never move** — the region grid, back panel, shelves, doors, drawers and hinge boring are all unaffected (like the overlay back). Panels are tagged `panelData` (function `Tamponamento`, grain-locked `Girar=Nao`, front edge banded with the fronts tape) so they reach the cut list; their slot names (`Tamponamento Esquerdo`/`Direito`/`Superior`) flow through appearance capture and `panel_overrides` like any other body. Exposed as a gated **Tamponamento (acabamento)** group in the New/Edit dialog (material dropdown carries a `(mesmo do corpo)` = inherit entry), a **Tamponamento** section in the Cabinet Layout palette, and a section in Preferences — both palettes lead the section with a static `tamponamento` reference schematic (front elevation of the three applied panels + a top view calling out `front_overhang`), drawn from the shared `DIAGRAMS` table. **v1 limitation:** the panels extend past the nominal `W×H` envelope, but the published `fmob_*` user parameters and multi-cabinet `translation` spacing still use the nominal `W×H×D` (fine for a single exposed-end cabinet).
- **Arremate (ajuste até teto/parede):** optional scribe / gap-filler pieces that let a cabinet "reach" an uncertain ceiling and/or side walls — standard BR practice is to build the carcass a little short and close the gaps with **front trim pieces cut oversized and scribed/trimmed on site**. Configured per cabinet via `cfg['arremate']` (module-level `ARREMATE` defaults, deep-merged in `normalize_cfg` like `tamponamento`/`joinery`/`hinge`/`tol`/`fita`). Eleven keys: a top toggle (`top`) whose valance height (the carcass-top→ceiling gap) is set one of two ways per `top_gap_mode` — **`'gap'`** (default) reads `top_gap` (mm) directly, **`'ceiling'`** derives it from `ceiling_height` (mm, total floor→ceiling room height) minus the cabinet height `H`, so the user can enter the room's ceiling height and the gap is computed. The pure **`resolve_arremate_top_gap(cfg)`** (`max(0, ceiling_height − H)` in ceiling mode, else `top_gap`) is the single seam the builder and `validate_cfg` both read the effective gap through, so they can't drift; plus `top_inline_fronts` (face the sanefa with the fronts, see below) and `top_side_returns` (U-shape wrap, on by default, see below), two side toggles (`left`/`right`) sharing `side_gap` (mm, the carcass-side→wall gap = each strip width), a thickness `t` (mm), and a `material` (blank `''` inherits the carcass). Two kinds, both modelled as thin **front boards** (thickness in Y, **front face flush with the carcass front `y=0`**, occupying `y ∈ [0, t]`), grain-locked (`Girar=Nao`) and banded with the fronts tape like a visible front — the user chose *sanefa frontal* + *régua frontal* + *faceado, envelope cresce*: (1) the **top sanefa** is a valance spanning the carcass width (`x ∈ [0, Wc]`) standing from the carcass top `Hc` up by `top_gap` to meet the ceiling (open behind — hides the gap from the front, giving the "full height" look); (2) each **side régua** is a front filler strip beside a carcass side (`side_gap` wide in X), running the **full finished height** — floor→ceiling (`Hc + top_gap`) when a top sanefa is present, else floor→carcass-top — scribed to the wall. Like Tamponamento they sit **outside** the box, so the envelope grows (up by `top_gap`, out by `side_gap` per side) and the **interior datums never move** (region grid, back, shelves, doors, drawers, hinges all unaffected). Sides run full height while the sanefa spans only between them, so the pieces **never overlap**. **`top_inline_fronts`** faces the sanefa with the doors/drawers instead of leaving it recessed: overlay fronts project forward by their own thickness (door front at `y=−door_t`, drawer face at `y=−face_t`), so a sanefa flush at `y=0` sits *behind* the front plane (visible in the model as a recessed valance). With the flag on, the structural sanefa stays flush at the carcass front and a **second facing sheet** (`Arremate Superior Frente`) is added in front of it (`y ∈ [−front_reach, 0]`), its depth `front_reach` filling the gap so its visible face lands exactly on the overlay front plane. `front_reach` = the max overlay reach of the enabled non-inset fronts (`door_t` and/or drawer `face_t`); it is a **no-op** when the fronts are all inset (front already at `y=0`) or absent. **`top_side_returns`** (on by default) wraps the sanefa into a **U**: a full-depth return board sits directly above each carcass side (`x ∈ [0,t]` / `[Wc−t,Wc]`, `y ∈ [front_y0, Dc]`, at the gap height), so exposed ends read as the sides continuing to the ceiling; to avoid sharing volume the front board then spans only **between** the returns (`x ∈ [t, Wc−t]`) and they butt at `x=t`/`x=Wc−t` (without the U the front board spans the full carcass width). The returns inherit the faced front plane (`front_y0 = −front_reach`) when `top_inline_fronts` is on, so the whole U comes forward together. Return slots `Arremate Superior Retorno Esquerdo`/`Direito`; their visible (forward) edge is the `top_gap`-length edge, banded via `bands={'b':…}`. Panels are tagged `panelData` (function `Arremate`; slot names `Arremate Superior`/`Esquerdo`/`Direito`/`Superior Frente`/`Superior Retorno Esquerdo`/`Superior Retorno Direito` flow through appearance capture + `panel_overrides` like any other body); each `Complemento` carries an *"ajustar no local"* note so the shop cuts it oversized and trims on install (cut-list only — no *usinagem*). Exposed as a gated **Arremate (ajuste)** group in the New/Edit dialog (a *Medida da sanefa* dropdown picks the mode and shows only the matching field — *Folga até o teto* or *Altura do teto (piso→teto)* — toggled by `_apply_arremate_top_mode_visibility` from the New/Edit `inputChanged` handlers; material dropdown carries a `(mesmo do corpo)` = inherit entry), an **Arremate (ajuste)** section in the Cabinet Layout palette (which also shows a live *folga calculada* readout in ceiling mode via `renderArremateMode`), and a section in Preferences — both palettes lead the section with a static `arremate` reference schematic (front elevation of the sanefa + side réguas against ceiling/walls, plus a top view of the U returns), drawn from the shared `DIAGRAMS` table (same mode dropdown + conditional row, wired by `wireArremateMode`). `validate_cfg` requires `t>0` for any enabled piece, a positive `side_gap` for the enabled side pieces, and — for an enabled top sanefa — either a positive `top_gap` (`'gap'` mode) or a `ceiling_height` greater than `H` (`'ceiling'` mode). **v1 scope:** side and top gaps are closed by independent pieces; **combining arremate with tamponamento on the same side is out of scope** (they would share volume). Same envelope caveat as Tamponamento — `fmob_*` params and multi-cabinet spacing use the nominal `W×H×D`.
- **Doors** (*portas*) are frameless: N equal doors on the front face, separated from each other by an even reveal gap (*folga*), edge-banded on all four edges and grain-locked (`Girar=Nao`). A `door_inset` flag (checkbox *Porta embutida (inset)*) picks the mounting style: **overlay** (*sobreposta*, default) mounts the doors forward of the Y=0 front plane, spanning the full carcass width inset from the edges by the gap; **inset** (*embutida*) seats them inside the clear opening (width `W−2t`, height `Hbox−2t`), flush with the front face, with the gap as the reveal all round. Either way they cover the carcass box front (not the toe kick). **Shelf depth** has two modes, chosen by the `shelf_align_front` flag (checkbox *Prateleiras alinhadas com a frente*): **shallower** (default) recesses every shelf from the front by `shelf_front_setback` (default 30 mm), while **aligned** (flag on) makes them flush with the carcass front (base setback 0). On top of the chosen base setback, shelves are always pushed back far enough that a closed door clears them (an inset door reaches `door_t` into the opening, an overlay door needs only a small gap — the `shelf_door_clearance` tolerance); the effective setback is `max(base_setback, door reach)`, so even frame-aligned shelves never conflict with an inset door. Doors are **not** part of the rigid carcass — each gets its own vertical **pivot (revolute) joint** on its outer vertical edge (hinge) so it opens like a real hinged door. Doors left of centre hinge left, the rest hinge right (a two-door pair meets in the middle). Since both hinge edges run +Z, a positive rotation swings both the same rotational sense; the swing is therefore limited per side — right-hinged doors `0…+110°`, left-hinged doors `−110…0°` — so each only opens outward.
- **Hinge boring** (concealed *dobradiça de caneco*, optional `with_hinges`, on by default when doors are enabled) is **model-only geometry**, cut with the same `TemporaryBRepManager` boolean-difference path as the dado grooves — cylinders instead of boxes (`_make_temp_cylinder`; `add_solid_panel` now takes a `holes=` list of `(x0,y0,z0,x1,y1,z1,radius)` cm tuples). Each door gets a blind **35 mm cup bore** in its interior-facing back face (Y=0 for overlay, Y=+`door_t` for inset), inset from the hinge-side edge; the hinge **count scales with door height** (`hinge_count_for_height`: 2 ≤900 mm, 3 ≤1600 mm, 4 ≤2000 mm, else 5), first/last inset 100 mm from the ends and the rest evenly spaced. The matching **mounting-plate screw pilots** are bored into the adjacent side panel's interior face — but only for the **outermost doors**, whose hinge edge sits at a real side panel; a frameless carcass has no interior divider for inner doors (>2) to mount to, so those get cups only. Boring dimensions are **per-cabinet** (`cfg['hinge']`, defaults from the module-level `HINGE` dict, filled in by `normalize_cfg` for older stored configs); five knobs — cup diameter, cup depth, edge-to-cup-centre, end inset, and shelf clearance — are editable in the **Advanced** section, while the plate screw-pilot specifics stay at the `HINGE` defaults. **None of this reaches the CSV** — CorteCloud's format has no *furação* field — so the per-door hinge count is appended to the door's `Complemento` as a note instead.
- **Hinge/shelf collisions:** the only real clash is a hinge plate landing at the same height as a shelf (both mount to the side panel's interior face; the cup bore itself never collides, as it cuts into the door toward −Y while shelves sit at +Y). Shelf positions (`shelf_z_bottoms`, shared by the builder and the check so they can't drift) are compared against the hinge Z's; any hinge within `HINGE['shelf_clearance']` of a shelf band is **auto-nudged** to the nearest clear position within the door (`resolve_hinge_conflicts`) — the cup and plate share the same nudged Z so they stay aligned. A hinge that can't be cleared (a crowded door) is left in place and reported via a non-fatal note in the New/Edit Cabinet result dialog (`build_cabinet` returns a `warnings` list).
- **Drawers** (*gavetas*) are a single column of N stacked drawers across the carcass front, laid out like doors via a `drawer_inset` flag (overlay default / *embutida*). Each drawer is a full BR-standard **box** — 2 sides + a box front + a box back (from `drawer.box_t`, default **16 mm** — the side thickness the UM A30 is designed for; functions `Lateral`/`Travessa`) plus a **bottom** seated in a dado groove cut into all four walls (`drawer.bottom_t` ≈6 mm, `Fundo`), same boolean-groove path as the back panel — plus a separate **face** (*frente*, `drawer.face_t` ≈18 mm, function `Porta`, banded all four edges, `Girar=Nao`). All six are tagged `panelData` → they go in the cut list. Box sizing is driven by the slide's real planning spec through **one number, `slide_side_space(spec, box_t)`** — the space the runner takes on *each* side, between the carcass and the **outer** box side — so the outer box width is always `clear_width − 2·side_space` and the box is centred with that air gap per side. A **side-mounted** runner publishes it directly (`side_space`: ~12,7 mm for a *telescópica* 45 mm, ~12,5 mm for a *roldana*), which is why it eats far more width than an **undermount** (~6,5 mm); undermount datasheets instead publish a `carcass_deduction` on the bottom *between* the sides (42 mm for the Matrix Invisa A30), and `slide_side_space` converts it (`deduction/2 − box_t`, = 5 mm with 16 mm sides) so the classic geometry is reproduced exactly. Box depth = `min(recommended_box_depth (≈NL), back-of-cabinet − back_clearance)`; and `validate_cfg` enforces the slide's `min_cabinet_depth` (and rejects a region too narrow to leave the box any width once both runners are deducted). **Faces** stack over the front region (overlay = full carcass front, inset = clear opening) with the reveal `drawer_gap`; each **box** is laid out behind its own face: the box floor sits a `bottom_clearance` runner gap above the face bottom (but never below the carcass base), and the box top stops `drawer.box_top_gap` (~30 mm) below the face top / interior ceiling, so a short box rides behind the tall face and never fouls the drawer above. Aligning the box to its face (rather than to an independent interior grid) is what keeps the bottom drawer from sitting too high. Box side height is whatever that leaves, capped by `drawer.box_height` (default 150 mm) for very tall single drawers. Box/bottom sub-specs live in the module-level `DRAWER` dict (deep-merged in `normalize_cfg` like `hinge`/`tol`); only the two materials + face band are exposed in the dialog. **The model is organised into components under the cabinet**: the carcass box (`Corpo`) and the toe kick (`Rodape`) are sub-assemblies of their panel-components, each locked with a rigid group (`_rigid_group_occs`); each drawer is **one component (`Gaveta N`) whose parts are bodies** (via `add_solid_body`, not child components) so the whole drawer is inherently rigid and can take a slider joint off its own geometry. Everything is still built at the same cabinet-local coordinates (all these components carry identity transforms). The carcass + toe kick are rigid-grouped into one grounded structure; doors pivot and each drawer gets a **slider (prismatic) joint** — anchored to the grounded `Corpo`, its axis a Y-running edge of the drawer's own box-side body (`attach_drawer_slides` + `_find_horizontal_y_edge`; as-built joints need real geometry for non-rigid motion, so `None` — which only works for rigid joints — silently fails). Travel is limited to `0.9·box_depth` of movement toward the **front**, at rest closed (0). The slide axis is a `CustomJointDirection` over a body edge, and an edge's direction is whatever the BRep hands back — the box sides are cut by a boolean difference (the bottom groove), which can flip the surviving edge — so the forward direction is **measured, never assumed**: `_slide_forward_sign` reads the joint's own `slideDirectionVector` (falling back to the edge's start→end vector) and `_set_drawer_travel_limits` puts the range on the side that actually opens the drawer — `[0, +travel]` when the axis points −Y, `[−travel, 0]` when it points +Y. Hardcoding the positive side is what used to make some drawers slide *into* the carcass. With the region grid a drawer stack now fills whatever *band* its leaf occupies (box width derives from the band's clear width, not `W−2t`), so drawers can share a cabinet with shelves/doors in sibling regions — the old shelves-vs-drawers exclusion no longer applies.
- **Drawer slide hardware** is chosen from a bundled **library manifest** (`resources/hardware/hardware.json`, keyed by `slide_key`). Every spec declares a **`mount`** — the one thing that changes the geometry: **`side`** (*lateral*, mounted on the drawer's side: `roldana_*` extração parcial and `telescopica_h45_*`/`h35` extração total, 250–500 mm) or **`undermount`** (*oculta*, under the box: the generic BR `oculta_softclose_*` 350–500 mm and the *Häfele Matrix Invisa A30 GT2 300 mm*, the only entry shipping a CAD model). The default is `telescopica_h45_350`, the common BR side runner that fits the default 400 mm-deep cabinet. `resolve_slide_spec(cfg)` returns the full spec (all mm) backfilled from the module-level `FALLBACK_SLIDE`, so the mounting spec (`side_space` *or* `carcass_deduction`, `bottom_clearance`, `back_clearance`, `min_cabinet_depth`, `recommended_box_depth`, `profile_z_offset`; `side_clearance`/`side_panel_thickness`/`base_depth_offset` are informational) lives in the manifest and switching slides re-sizes the boxes automatically (the hardware analogue of how `HINGE` defaults fill in). Because the manifest sits in the read-only install folder, five of those numbers are **overridable per cabinet** via `cfg['slide']` (module-level `SLIDE`, deep-merged in `normalize_cfg` like `hinge`/`drawer`/`tol`): `side_space`, `bottom_clearance`, `back_clearance`, `box_depth` → `recommended_box_depth`, and `min_cabinet_depth`. They are applied by `resolve_slide_spec` **only while `custom` is True** (an explicit `side_space` then also clears `carcass_deduction`, so it wins over the datasheet rule); with `custom` off the library spec is authoritative and the stored numbers are inert. All three UIs share that contract: the New/Edit dialog's *Gavetas* group, the Cabinet Layout palette's *Frentes & ferragens* section and the Preferences *Gavetas* section show the five fields as a **read-only live readout** of the selected slide (refreshed from `slide_ui_values` / `slide_specs_for_ui` when `slide_key` changes) until *Personalizar* is ticked, at which point they become editable and are never overwritten by a slide change. Representation is **hybrid**: ticking *Inserir modelo 3D da corredica* (`insert_real_hardware`) imports the real bundled CAD; otherwise a lightweight parametric **proxy** box marks each slide, positioned by the pure `slide_proxy_slots` — for `side` mounts a plate filling the air gap beside each box side (`side_space` thick, `proxy_H` tall, from `profile_z_offset` above the box floor), for undermounts the classic box in the runner gap directly under the box (height = `bottom_clearance`, width `proxy_W`), both `proxy_L` long along Y. The real model is imported **once, up front, before the cabinet component exists** (`import_hardware_component`) — CAD (`.step/.stp/.f3d/.iges`) via `ImportManager.importToTarget` into the **root** (importing into a freshly created child mid-build invalidates the in-progress assembly — Fusion then raises *"refers to a deleted Object"*), mesh (`.obj/.stl/.3mf`) via `meshBodies` in a child holder. That imported component is then **instanced** (`occurrences.addExistingComponent`, positioned by `_matrix_from_transform` from the spec's `model_transform`) at each slide slot at the end of the build, grounded, and the temporary root import is deleted; multi-drawer docs stay light because the geometry is shared. Import is guarded — a missing/failed model just falls back to the proxy, never aborting the build. **Neither proxy nor model carries `panelData`**, so hardware never reaches the CSV (like hinges); the chosen slide is appended to the drawer face's `Complemento` instead. Bundled models go under `resources/hardware/models/` and should be **closed-state STEP** (clean, light); the imported real model is fixed (grounded), since a single body's rails aren't separable, while the drawer box slides.

## CSV format (CorteCloud "importar do Excel")

Semicolon-delimited (`;`), UTF-8 with BOM. Columns:

```
Quantidade;Comprimento;Largura;Funcao;Fita C1;Fita C2;Fita L1;Fita L2;Material;Complemento;Girar
```

`Comprimento` is the larger face dimension, `Largura` the smaller. `Girar` (`Sim`/`Nao`) tells CorteCloud whether it may rotate the part during nesting (grain lock). See [cortecloud_importar.csv](cortecloud_importar.csv) for a sample export.

## Versioning

The add-in version lives in **two places that must stay in sync**: `version` in [FusionMob.manifest](FusionMob/FusionMob.manifest) and `__version__` in [FusionMob.py](FusionMob/FusionMob.py). It follows semantic versioning (`MAJOR.MINOR.PATCH`).

**IMPORTANT: increment the PATCH version (the last digit) on every modification to the add-in.** Bump MINOR for new features and MAJOR for breaking changes, resetting the lower digits as usual. Always update both files together.

## Development notes

- Python add-in using the Fusion 360 API (`adsk.core`, `adsk.fusion`). Entry points: `run(context)` (registers UI) and `stop(context)` (tears it down). Nearly everything lives in `FusionMob.py`; the non-Python, non-icon assets are `resources/ui/layout_editor.html` (Cabinet Layout palette) and `resources/ui/preferences.html` (Preferences palette) — both self-contained HTML/CSS/JS, no external deps. User preferences persist to `preferences.json` in a writable per-user dir (see *User preferences* above), loaded lazily and cached like the hardware manifest. Runtime data dependency: `resources/hardware/hardware.json` (the drawer-slide library), loaded lazily and cached; degrades to the built-in `FALLBACK_SLIDE` if absent.
- **Cabinet Layout palette** (`Palettes.add` with the HTML file) talks to Python over `palette.incomingFromHTML`: JS calls `adsk.fusionSendData(action, jsonString)` and Python replies by setting `HTMLEventArgs.returnData`. Actions: `init` (option lists + cabinets + a default cfg), `selectTarget` (load a cabinet's stored cfg), `validate` (run `validate_cfg` only), `apply` (validate → capture position → delete old occ → `build_cabinet` → return the new token + refreshed cabinet list). Apply reuses the exact delete-and-rebuild flow Edit Cabinet uses. Pure layout logic (`normalize_cfg`, `split_child_extents`, `plan_layout`, `validate_cfg`, `_validate_leaf`) has no `adsk` dependency and can be unit-tested by stubbing `adsk.core`/`adsk.fusion`.
- Requires an **Assembly or Hybrid** design (not a Part design — those allow only one component); the code raises a friendly `PartDesignNotSupportedError` otherwise.
- Comments and UI labels mix English and Portuguese, matching the target audience.
- Began as "Phase 1" (parametric panel editor + cut-list exporter); has since grown a full carcass generator, doors with concealed-hinge boring, and drawers with embedded slide hardware (the first feature to import external CAD rather than build geometry from scratch).
- **Importing external CAD** (real drawer-slide models) is the exception to the from-scratch geometry rule — prefer lightweight closed-state STEP; mesh imports (`.obj/.stl/.3mf`) work but are heavy, and multiple drawers × 2 rails can slow rebuilds, which is why the proxy is the default and `insert_real_hardware` is opt-in.
